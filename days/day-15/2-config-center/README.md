# Day 15 · 设计题：分布式配置中心

## 背景

一个公司有几百个微服务、几万个实例。每个服务都有很多配置：数据库地址、超时时间、限流阈值（Day 3）、熔断参数（Day 11）、功能开关（新功能先对 1% 的用户打开）。

最原始的做法是把配置写在每个服务的配置文件里，改一个超时时间要重新打包、重新发布几千台机器，十几分钟后才能生效。出了故障想紧急调大限流阈值，根本来不及。

**配置中心** 解决的就是这个问题：配置集中存放，修改后 **秒级推送** 到所有实例，不用重启。携程的 Apollo、阿里的 Nacos、Spring Cloud Config、以及直接用 etcd / ZooKeeper / Consul 的 KV，都是这一类系统。

它看起来是个简单的 CRUD 系统，但有几个很硬的要求：

- **它挂了不能连带所有服务挂掉**。配置中心是所有服务的依赖，它的可用性要求比任何业务都高。
- **配置改错了就是全站事故**（历史上很多大故障都是一次错误的配置推送）。所以要有灰度、回滚、审计。
- **一致**：同一个服务的几千个实例，不能有的拿到新配置、有的永远停在旧配置上。

今天的动手题 Raft 就是 etcd 保证「配置数据本身不丢、不分叉」的基础。

## 题目

为一家公司设计 **统一配置中心**。

**功能需求**

- 配置按 **应用 → 环境（dev / test / prod）→ 集群（机房）→ 命名空间** 组织，每个命名空间是一组 key-value。
- 在管理后台修改配置，点击「发布」后，相关实例 **秒级** 收到新配置并生效（不重启）。
- **版本管理**：每次发布都是一个版本，可以一键 **回滚** 到任意历史版本。
- **灰度发布**：新配置先推给指定的几台实例（或按比例），观察没问题再全量发布。
- **权限与审计**：谁能改哪个应用的配置、谁在什么时候改了什么，都要记录；生产环境的修改需要审批。
- 客户端 SDK：业务代码通过 SDK 读取配置，并能注册「配置变化时的回调」。

**非功能需求**

- **配置读取的可用性极高**：即使配置中心整个挂了，已经在运行的服务也要能正常工作，新启动的实例也要能启动起来。
- 推送延迟：发布后 **1 秒** 内 99% 的实例收到新配置。
- 配置数据绝对不能丢、不能出现两个不同的「当前版本」。

**规模（已知条件）**

- **500** 个应用，**5 万** 个实例（客户端），分布在 **3** 个机房。
- 每个应用平均 **10** 个命名空间，每个命名空间平均 **5 KB**。
- 配置修改不频繁：全公司每天约 **1000** 次发布。
- 每个客户端启动时拉取一次全量配置，之后只接收变更。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：全部配置数据有多大？一次发布要推送给多少个实例、多少数据？5 万个客户端同时保持着连接（或者轮询），对服务端意味着什么？如果所有实例同时重启（比如机房断电恢复），启动时拉取全量配置的峰值 QPS 是多少？
2. **API**（第 3 节）：管理端（创建、修改、发布、回滚、灰度）和客户端（拉取配置、监听变化）两类接口。客户端怎么告诉服务端「我已经有哪个版本了」，好让服务端只在有变化时才返回数据？
3. **数据模型**（第 4 节）：配置项、发布版本、灰度规则、审计日志分别怎么存？为什么「发布」要生成一个 **不可变的快照**，而不是直接修改当前配置？回滚怎么实现？
4. **高层架构**（第 5 节）：管理后台 → 配置服务（写）→ 存储 → 通知 → 推送服务 → 客户端 SDK（本地缓存 + 回调）。管理端和客户端访问的服务要不要分开？为什么？
5. **配置怎么推到客户端**（第 6 节，最重要）：对比下面三种方式，选一种并说明理由：
   - 客户端定时轮询（每 30 秒拉一次）
   - **长轮询**（客户端发请求，服务端在有变化或超时（比如 60 秒）时才返回）。Apollo 和 Nacos 就是这么做的
   - 服务端主动推送（WebSocket / gRPC stream）
   
   还要回答：推送失败或者通知丢了怎么办？（长轮询 + 定期全量对账兜底）客户端怎么知道自己拿到的是最新版本？
6. **存储与一致性**（第 6 节）：配置数据存在哪里？
   - 直接用 **etcd / ZooKeeper**（基于 Raft / ZAB，自带 watch 机制）：好处？为什么它们不适合直接让 5 万个客户端都连上来？
   - 用 **MySQL** 存配置 + 自己做推送服务：好处？怎么保证推送服务之间、多个机房之间看到的版本一致？
   - 结合今天的动手题解释：为什么 etcd 用 3 或 5 个节点、而不是 2 个或 4 个？etcd 的 leader 挂了，配置读写会中断多久？
7. **高可用与容灾**（第 7 节）：
   - 客户端 SDK 怎么做到「配置中心挂了也不影响业务」？（内存缓存 + **本地磁盘快照**，启动时先读本地文件）
   - 跨机房：每个机房一套推送服务？配置写入只在一个主机房吗？主机房挂了怎么办？
   - 「重启风暴」：5 万个实例同时启动，同时拉全量配置，怎么不把配置中心打挂？
8. **安全的发布**（第 7 节）：灰度发布怎么实现（灰度规则下发给谁、客户端怎么判断自己是否在灰度里）？发布了一个错误配置（比如把超时改成了 0），怎么尽量减少影响、怎么快速回滚？配置项要不要做格式校验？
9. **取舍**（第 8 节）：至少 3 行，比如推 vs 拉、etcd vs MySQL + 自建推送、强一致 vs 可用性。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 6 节画出 **一次发布** 从「点击发布」到「5 万个实例的回调被触发」的完整时序，标出每一步可能失败的地方，以及失败后最终怎么保证所有实例都拿到新版本。
- 第 7 节写清楚客户端 SDK 在下面三种情况下各自的行为：配置中心正常、配置中心全部不可用、配置中心不可用时实例重启。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- 配置中心本身也需要配置（比如它自己的数据库地址）。这个「鸡生蛋」的问题怎么解决？
- 有些配置需要 **多个 key 一起生效**（比如数据库地址和密码要同时换）。客户端怎么避免先拿到新地址、后拿到新密码的中间状态？
- 「服务发现」（一个服务有哪些实例、实例的 IP 和端口）和「配置中心」有很多相似之处，Nacos 就把两者做在一起。它们在一致性要求上有什么区别？（提示：服务实例列表短暂不一致可以接受吗？）
- 功能开关（feature flag）要做到「按用户 ID 的 5% 灰度」，这个判断是在配置中心做，还是在客户端 SDK 做？为什么？
- 密钥、数据库密码这类敏感配置，能和普通配置一样存吗？

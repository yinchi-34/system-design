# Day 16 · 设计题：云盘文件同步（类 Dropbox / 百度网盘 / iCloud Drive）

## 背景

在电脑上的一个文件夹里改了一个文件，几秒钟后，手机和另一台电脑上的同一个文件也变了。这就是云盘同步。它的难点和前面所有的题都不一样：

- **文件大**：一个文件可能几 GB。改了 PPT 里的一个字，难道要把整个 500 MB 的文件重新上传一遍？→ **分块**，只传变化的块（今天的动手题 Merkle 树能快速找出哪些块变了）。
- **数据重复多**：一百万个用户都上传了同一部电影、同一个安装包。→ **按块去重**，相同内容的块只存一份，甚至「秒传」。
- **多设备、离线、冲突**：笔记本在飞机上离线改了一个文件，同时手机上也改了同一个文件。落地联网后怎么办？
- **元数据比数据更难**：文件名、目录结构、版本、谁共享给了谁、每个设备同步到了哪一步。这些元数据要强一致，而文件内容可以放在便宜的对象存储里。

## 题目

设计一个 **云盘文件同步服务**。

**功能需求**

- 用户在客户端（Windows / macOS / 手机）的同步文件夹里新建、修改、删除、重命名、移动文件和目录，变化自动同步到云端，再同步到该用户的其他设备。
- 支持 **离线修改**，联网后自动同步。
- **版本历史**：每个文件保留最近 30 天的历史版本，可以恢复。
- 文件 / 文件夹 **共享**：分享给其他用户，对方可以查看或编辑，修改同样会同步。
- 发生 **冲突**（两个设备同时修改同一个文件）时不丢任何人的修改。
- 单个文件最大 **50 GB**。

**非功能需求**

- 可靠：用户的文件 **绝对不能丢**、不能损坏。
- 同步延迟：在线设备在 **几秒** 内看到其他设备的修改。
- 节省带宽和存储：修改大文件只传变化部分；相同内容只存一份。
- 规模大但大多数文件很少变化。

**规模（已知条件）**

- 注册用户 **5 亿**，日活 **1 亿**，平均每个用户 **3** 台设备。
- 每个用户平均存储 **10 GB**，平均 **2000** 个文件。
- 每个日活用户每天平均修改 / 新增 **20** 个文件，平均文件大小 **2 MB**。
- 块大小 **4 MB**。按块去重后，实际存储约为逻辑存储的 **60%**。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：总逻辑存储和去重后的实际存储（含 3 副本）？每天新增多少数据？每秒有多少次文件修改（平均 / 峰值）？元数据有多少条（文件数 × 版本数），大概多大？
2. **API**（第 3 节）：客户端和服务端之间至少需要这几类接口：上传块、提交文件元数据（「这个文件的新版本由哪些块组成」）、拉取变更（「从我上次同步的位置开始，有哪些变化」）、下载块。为什么 **块的上传** 和 **元数据的提交** 要分成两步？
3. **数据模型**（第 4 节，重要）：
   - **块存储**：块以什么为 key 存储（内容的哈希）？为什么这样就自动实现了去重？块存在哪里（对象存储）？
   - **元数据**：文件表（文件 ID、路径、所属命名空间、当前版本）、版本表（版本号、块哈希列表、修改设备、时间）、命名空间（一个用户的网盘、一个共享文件夹）。用什么数据库？按什么分片？为什么元数据需要事务和强一致？
   - **变更日志**：每个命名空间一条单调递增的变更序列（「journal」），设备记住自己同步到了第几条。
4. **高层架构**（第 5 节）：客户端（文件监听 → 分块 → 计算哈希 → 本地数据库记录同步状态）、块服务（上传下载块，直接对接对象存储）、元数据服务、通知服务（告诉在线设备「有新变化，快来拉」）。画出「设备 A 修改一个文件 → 设备 B 看到新版本」的完整路径。
5. **只传变化的部分**（第 6 节，最重要）：
   - 文件切成 4 MB 的块，每块算哈希。修改后重新切块算哈希，和上一个版本对比，只上传哈希不同的块。对超大文件（50 GB = 12800 块），用 Merkle 树（今天的动手题）怎么更快地比较？
   - 上传前先问服务端「这些哈希你已经有了吗」，已有的块直接跳过（**秒传** 和 **跨用户去重**）。
   - 在文件 **中间插入** 一段内容，固定大小切块会导致后面所有块都变。怎么办？（内容定义分块，见动手题的进阶）
6. **同步与冲突**（第 6 节）：
   - 设备怎么知道有新变化？（长连接 / 长轮询通知 + 按游标拉取变更日志，Day 15 配置中心的思路）
   - 设备离线时改了文件，联网后提交时，服务端发现这个文件已经被别的设备改过（提交时带上「我是基于哪个版本修改的」）。怎么处理？（Dropbox 的做法：保留双方，把一方重命名为「xxx（冲突副本）」）
   - 为什么不尝试自动合并文件内容？
7. **可靠性与扩展**（第 7 节）：
   - 块上传了一半断网怎么办？（Day 17 的断点续传）元数据已提交、但块还没传完会怎样？（必须先传完块、再提交元数据）
   - 去重后，一个块被很多文件引用。删除一个文件时，块什么时候能真正删除？（引用计数 vs 定期标记清除；为什么不能马上删）
   - 元数据库怎么分片？一个共享文件夹被 1 万个人共享，它的变更要通知 1 万台设备，怎么办？
   - 热门文件（一个被分享了百万次的文件）的下载怎么扛？（CDN）
8. **安全**（第 7 节）：按内容哈希做跨用户去重，会带来什么隐私问题？（攻击者可以通过「秒传是否成功」来判断别人是否有某个文件）怎么缓解？
9. **取舍**（第 8 节）：至少 3 行，比如块大小（大块 vs 小块）、跨用户去重 vs 隐私、冲突自动合并 vs 保留冲突副本。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 4 节写出文件、版本、块、变更日志这几张表的主要字段，并说明「一个文件的一个版本」是怎么由块拼起来的。
- 第 6 节画出 **离线冲突** 的时序：设备 A 和 B 都基于版本 5 修改了同一个文件，A 先提交成功（版本 6），B 后提交时发生了什么、最终两台设备上各有什么文件。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- 块大小选 4 MB 有什么讲究？选 64 KB 或 64 MB 会怎样（去重率、元数据量、上传请求数）？
- 用户删除了一个文件，30 天后才真正删除。用户反悔了想恢复，怎么实现？用户想立刻彻底删除（合规要求），去重的块又被别人引用着，怎么办？
- 客户端怎么高效地发现本地文件变了（文件系统事件 vs 定期扫描）？客户端重启后怎么知道哪些变化还没同步？
- 「选择性同步」：用户只想在笔记本上同步部分文件夹，其余的只在云端。客户端和服务端要怎么支持？
- 如果要支持多人 **实时** 协同编辑同一个文档（Google Docs），今天这套「整个文件为单位的版本 + 冲突副本」还够用吗？（Day 28 会讲）

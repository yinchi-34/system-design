# Day 06 · 设计题：分布式唯一 ID 服务

## 背景

订单号、支付流水号、消息 ID、帖子 ID……几乎每个业务都要一个「全局唯一的 ID」。听起来是最简单的一道题，但面试官喜欢它，因为它很快就会逼出几个本质问题：

- **唯一** 靠什么保证？靠中心化的计数器（单点、瓶颈），还是靠「每台机器有一个唯一编号 + 本地计数」（那么编号本身怎么唯一）？
- **有序** 有多重要？严格递增、趋势递增、完全随机，各自对数据库索引、分页、安全有什么影响？
- **时钟** 能不能信？Snowflake 把正确性押在机器时钟上，而时钟是会回拨的。
- **可用性**：ID 服务挂了，所有下单都失败。它必须比依赖它的业务更可用。

今天的动手题已经实现了两种核心算法，这道题要把它们变成一个公司级的服务。

## 题目

为一家电商公司设计 **分布式唯一 ID 服务**，所有业务（订单、支付、商品、消息、日志追踪）都从这里拿 ID。

**功能需求**

- 生成 **64 位整数** ID（要能直接放进 MySQL 的 `BIGINT` 主键）。
- ID **趋势递增**：大体上后生成的比先生成的大，用作 B+ 树主键时不会导致大量页分裂。
- 支持按业务隔离（订单 ID 和商品 ID 可以是不同的序列）。
- 提供批量获取：一次请求拿 N 个 ID。
- 能从 ID 里解析出生成时间（排查问题用）。

**非功能需求**

- 可用性 **99.999%**（一年停机不超过约 5 分钟）。ID 服务不可用就意味着所有下单失败。
- 延迟：p99 < 5 ms（含网络）。
- 绝对不能产生重复 ID，包括机器重启、时钟回拨、网络分区、机房切换的时候。
- 两个机房（同城双活），任意一个机房整体故障，另一个机房能继续发号。

**规模（已知条件）**

- 平时 **5 万 QPS**，大促峰值 **100 万 QPS**（每次请求平均要 1 个 ID，批量请求另算）。
- 服务器每台单核能发约 200 万个 Snowflake ID / 秒（内存操作），但受网络和 RPC 框架限制，每台约能处理 5 万个 RPC / 秒。
- 业务方有几百个服务，部署在 K8s 上，Pod 随时扩缩容、IP 会变化。
- 系统预计至少用 **30 年**。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **方案对比**（第 6 节，最重要）：至少比较下面 4 种方案，填一张表（唯一性靠什么、是否有序、是否依赖网络/数据库、性能、可用性、安全性），然后选一个（或组合），说清楚为什么：
   - UUID / UUID v7
   - 数据库自增 + 多主步长（比如 2 个库，一个发奇数，一个发偶数）
   - 号段模式 + 双缓冲（Leaf-segment）
   - Snowflake
2. **估算**（第 2 节）：100 万 QPS 需要多少台 ID 服务器？Snowflake 的 41 位时间戳够不够用 30 年？5 位数据中心 + 5 位机器 ID 最多支持多少台机器，够不够？如果用号段模式，号段长度设多少才能让数据库在大促时每秒更新不超过 10 次？
3. **部署形态**（第 5 节）：独立的 ID 服务（RPC 调用）vs 以 SDK 形式嵌入每个业务进程（本地生成，零网络开销）。各自的利弊？你怎么选？
4. **机器 ID 分配**（第 6 节）：K8s 里 Pod 随时创建销毁，worker_id 怎么分配才能保证同一时刻没有两个进程用同一个 ID？
   - 写死在配置里 / 用 IP 后几位：为什么不行？
   - 用 ZooKeeper / etcd 的顺序节点或带租约的 key：租约过期但进程还活着（GC 停顿、网络分区）会怎样？
   - 32 个 worker_id 不够用了怎么办？
5. **时钟回拨**（第 6 节）：NTP 校时、闰秒、虚拟机迁移都可能让时钟回退。小回拨等待、大回拨怎么办？进程重启后丢了上一次的时间戳怎么办（提示：定期把最大时间戳写到 ZooKeeper/本地文件，启动时检查）？
6. **高可用与双机房**（第 7 节）：Snowflake 服务和号段服务分别怎样做到单机挂了、整个机房挂了都不影响发号？号段模式下数据库是单点吗？两个机房的号段/数据中心 ID 怎么划分才不会冲突？
7. **安全**（第 7 节）：订单号连续或者能解析出时间，会暴露每天的订单量。哪些 ID 可以暴露给用户，哪些不能？怎么做到「对外不可猜、对内有序」？
8. **取舍**（第 8 节）：至少 3 行。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 6 节画出你最终方案的 **64 位布局**（每个字段几位、为什么这么分），以及「一个 Pod 启动 → 领到 worker_id → 发号 → 租约续期 → 优雅下线」的时序。
- 写清楚至少 **3 种会导致重复 ID 的故障场景**，以及你的设计怎么防住它们。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

- 为什么说 UUID v4 当 InnoDB 主键很糟糕？UUID v7 解决了什么？如果必须 128 位，你会选 UUID v7 还是 Snowflake 扩展到 128 位？

# Day 20 · 设计题：酒店预订系统（类携程 / Booking.com / Airbnb）

## 背景

酒店预订看起来和 Day 12 的秒杀很像（都是「抢有限的库存」），但有几个关键区别：

- **库存是按天的**：一间房不是一件商品，而是「这间房在 12 月 24 日这一晚」。订 3 晚，就要同时锁住 3 个日期的库存，任何一天没房都不行。
- **几乎不允许超卖**：秒杀超卖了可以给用户发个优惠券道歉；酒店超卖了，客人半夜到了前台没房住，是严重事故。但 **少卖**（明明有房却显示满房）也是直接的收入损失。
- **流程长、跨多个系统**：查价格 → 锁库存 → 支付 → 酒店确认 → 发通知。中间任何一步都可能失败，还有不少酒店的库存在 **第三方系统**（酒店自己的管理系统、渠道商）里，要通过接口去确认。→ **Saga**（今天的动手题）。
- **读远多于写**：用户会搜索、比价很多次才下一单。搜索量是下单量的几百倍。

## 题目

设计一个 **酒店预订平台**。

**功能需求**

- 搜索：按城市、入住日期、离店日期、人数搜索有房的酒店，显示每晚价格。
- 酒店详情页：房型、价格、剩余房间数（「仅剩 2 间」）。
- 下单：选房型和日期，锁定库存，支付，生成订单，发确认。
- 取消：按酒店的取消政策（免费取消 / 扣首晚房费）退款并释放库存。
- 酒店方：管理房型、价格（每个日期的价格可以不同）、库存。部分酒店的库存由它们自己的系统管理，通过接口同步。

**非功能需求**

- **不能超卖**，尽量不少卖。
- 下单（锁库存 → 支付 → 确认）的成功率要高，失败要能回滚干净，不能出现「钱扣了、房没订上」。
- 搜索延迟 **< 500 ms**，可以接受几分钟的库存延迟（下单时会再精确检查）。
- 节假日、大促时下单量是平时的 **10 倍**。

**规模（已知条件）**

- 酒店 **100 万** 家，平均每家 **50** 间房、**5** 种房型。
- 可预订的日期范围：未来 **365** 天。
- 日活 **2000 万**，每个日活用户平均搜索 **10** 次、看详情页 **5** 次。
- 每天 **100 万** 个订单，平均每单住 **2** 晚。
- 取消率约 **15%**。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：
   - 搜索 QPS 和下单 QPS（平均、峰值），读写比是多少？
   - 库存表有多少行（按「酒店 × 房型 × 日期」）？多大？一台 MySQL 放得下吗？
2. **API**（第 3 节）：搜索、详情、创建预订、支付回调、取消、查询订单。创建预订接口为什么要带 **幂等键**？（Day 11）
3. **数据模型**（第 4 节，重要）：
   - 酒店表、房型表、**房型库存表**（`hotel_id, room_type_id, date, total, reserved`）、价格表（同样按日期）、订单表、订单状态。
   - 为什么库存按「房型 + 日期」计数，而不是给每一间具体的房间建一行？什么时候才分配具体的房间号？
   - 订单的状态机：`pending → reserved → paid → confirmed`，以及 `cancelled`、`failed`。谁推动状态变化？
4. **高层架构**（第 5 节）：搜索服务（搜索引擎 + 缓存）、酒店 / 价格服务、库存服务、订单服务（Saga 编排器）、支付服务、通知服务、第三方酒店对接网关。画出搜索和下单两条路径。
5. **防超卖**（第 6 节，最重要）：
   - 订 12/24 到 12/27 三晚，怎么 **原子地** 锁住三天的库存？写出 SQL（`UPDATE ... SET reserved = reserved + 1 WHERE ... AND date IN (...) AND reserved < total`，检查影响的行数是否等于 3）。只锁了 2 天、第 3 天没房，怎么办？
   - 悲观锁（`SELECT ... FOR UPDATE`）、乐观锁（版本号）、条件更新，各适合什么情况？（Day 12）
   - 用户锁了库存但 15 分钟没支付，怎么释放？（订单超时，延迟队列，Day 21 会讲）
   - 「仅剩 2 间」的显示要实时吗？搜索结果里的库存可以有多大延迟？
6. **下单的 Saga**（第 6 节）：
   - 把下单写成 saga：每一步是什么、补偿是什么？哪一步是 **不可撤销** 的（pivot），应该放在哪里？
   - 支付成功了，但第三方酒店确认接口超时（不知道到底订上没有），怎么办？（查询 + 重试 + 人工兜底）
   - 用户取消订单也是一个 saga 吗？步骤是什么？
7. **可靠性与扩展**（第 7 节）：
   - 库存表按什么分片（`hotel_id`）？为什么同一家酒店的数据最好在同一个分片上？
   - 搜索为什么不直接查库存表？搜索索引怎么和库存、价格保持（近似）同步？（CDC / 消息队列）
   - 大促时一家热门酒店被几万人同时抢，这一行的锁争用怎么办？（Day 12 秒杀的思路能用多少？）
   - 第三方酒店系统很慢、经常挂，怎么不让它拖垮整个下单流程？（熔断，Day 11）
8. **取舍**（第 8 节）：至少 3 行，比如先锁库存再支付 vs 先支付再锁库存、允许少量超卖（航空公司的超售）vs 绝对不超卖、编排 vs 协同。

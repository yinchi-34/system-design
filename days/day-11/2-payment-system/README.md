# Day 11 · 设计题：支付系统（幂等、对账）

## 背景

前十天的系统，出错的代价通常是「用户体验差一点」：联想词旧了、Feed 晚了 5 秒、通知重复了一条。支付系统不一样，**错一分钱都是事故**：

- 用户点了一次「支付」，因为网络超时，App 自动重试了一次，**扣了两次钱**。
- 调用银行接口超时了，你不知道钱到底扣了没有。重试可能重复扣款，不重试可能漏扣（用户拿了货没付钱）。
- 你的数据库说「已支付」，银行说「没收到」，商户说「没到账」，三方各执一词。

所以支付系统的核心不是高并发，而是 **正确性**：

- **幂等**：同一笔支付无论被请求多少次，只扣一次钱。
- **状态机**：每笔支付都有明确的状态（创建 → 处理中 → 成功 / 失败），只能按规定的方向流转。
- **复式记账**（double-entry）：每一笔资金变动都同时记一借一贷，所有账户加起来永远平衡。
- **对账**：每天把自己的记录和银行 / 第三方渠道的账单逐笔核对，找出不一致并处理。

今天的动手题（重试 + 熔断）就是支付服务调用外部渠道时的「护甲」，但在支付场景下，**什么时候能重试** 是这道题的重点。

## 题目

为一个电商平台设计 **支付系统**：买家下单后付款，钱先进入平台账户，订单完成后结算给卖家。

**功能需求**

- **支付**：买家对一个订单发起支付，可以选择银行卡（通过收单银行 / 卡组织）或第三方钱包（类似支付宝、PayPal）。
- **退款**：全额退款和部分退款，一笔支付可以多次部分退款，但退款总额不能超过支付金额。
- **结算**：订单完成后，按天给卖家结算（扣除平台佣金），打款到卖家的银行账户。
- **查询**：买家、卖家能查到每一笔交易的状态；财务能查到平台每个账户的余额和流水。
- **对账**：每天和每个外部渠道对账，自动处理能处理的差异，处理不了的交给人工。

**非功能需求**

- **正确性第一**：不能重复扣款、不能丢钱、不能多退款。所有资金变动必须可审计、可追溯。
- 可用性 99.99%。外部渠道（银行、第三方钱包）经常超时或出故障，不能把故障传染给整个系统。
- 支付请求的延迟：p99 < 2 秒（主要耗时在外部渠道）。
- 合规：不能在自己的系统里存储完整的银行卡号（PCI DSS）。

**规模（已知条件）**

- 每天 **1000 万** 笔支付，大促峰值是平均的 **20 倍**。
- 平均每笔支付金额 100 元。
- 接入 **5 家** 外部支付渠道。外部渠道的平均响应时间 500 ms，有约 **0.5%** 的请求会超时（结果未知）。
- 交易记录保存 **10 年**。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：平均和峰值的支付 TPS？每天调用外部渠道时会有多少笔「超时、结果未知」的交易？10 年的交易和账务流水要多少存储？
2. **API**（第 3 节）：发起支付、查询支付、退款的接口。**幂等键** 由谁生成（客户端 / 订单服务 / 支付服务）、放在哪里（请求头 `Idempotency-Key`）？同一个幂等键第二次请求进来时，如果第一次还在处理中，返回什么？如果第一次已经成功，返回什么？如果参数和第一次不一样呢？
3. **数据模型**（第 4 节）：
   - 支付单、退款单的表结构，以及 **状态机**（画出状态和允许的转换，比如 `CREATED → PROCESSING → SUCCEEDED / FAILED`，哪些状态是终态）。怎么用数据库保证状态只能按规定方向变（条件更新：`UPDATE ... SET status='SUCCEEDED' WHERE id=? AND status='PROCESSING'`）？
   - **复式记账的账本**：账户表和分录表。用一个例子写出「买家支付 100 元 → 订单完成 → 平台抽佣 5 元 → 卖家结算 95 元」这个过程中产生的所有借贷分录，并说明为什么所有分录加起来恒为 0。为什么账本只能 **追加**、不能修改？
   - 金额用什么类型存储？为什么不能用浮点数？
4. **高层架构**（第 5 节）：画出一笔银行卡支付的完整路径：订单服务 → 支付服务（幂等检查、写支付单）→ 渠道路由 → 渠道适配层（调用外部渠道，带今天动手题的熔断和重试）→ 外部渠道 → 回调 / 轮询结果 → 更新支付单 → 记账 → 通知订单服务（消息队列，Day 7）。银行卡信息怎么处理才不落到你的系统里（托管支付页面 / 令牌化）？
5. **超时与重试**（第 6 节，最重要）：
   - 调用渠道超时，结果未知。你的支付单停在什么状态？接下来怎么确定结果（主动查询渠道的查单接口、等渠道的异步回调、日终对账兜底）？
   - 哪些调用可以直接重试，哪些绝对不能？调用渠道时你传给渠道的 **幂等键** 是什么（渠道是否支持幂等决定了你能不能重试）？
   - 渠道的异步回调可能重复、乱序、延迟几小时才到，甚至伪造。怎么处理（验签、幂等、状态机只前进不后退）？
   - 今天动手题的熔断器在这里怎么用？某家渠道熔断后，能不能自动切到另一家渠道？切换前要确认什么？
6. **一致性**（第 6 节）：支付单更新为成功、写账本分录、发消息通知订单服务，这三件事怎么保证要么都做、要么都不做？（本地事务 + **事务性发件箱**（transactional outbox）；为什么不用分布式事务 / 两阶段提交？）
7. **对账**（第 7 节）：
   - 每天渠道给你一个账单文件（几百万行）。怎么和你的记录逐笔核对？
   - 会出现哪几类差异（你有它没有、它有你没有、金额不一致、状态不一致）？各自怎么处理？
   - 除了和外部对账，内部的账本怎么自检（所有账户余额之和是否为 0、支付单和分录是否一一对应）？
8. **扩展与可用性**（第 7 节）：大促 20 倍流量时哪里是瓶颈（热点账户：平台的收款账户每笔支付都要更新余额）？怎么解决（拆成多个子账户、异步汇总、只追加流水不实时更新余额）？
9. **取舍**（第 8 节）：至少 3 行，比如同步等渠道结果 vs 异步回调、强一致记账 vs 最终一致、单一渠道 vs 多渠道路由。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 4 节画出支付单的 **状态机**，并写出复式记账的分录例子（表格形式即可）。
- 第 6 节写出支付服务处理一笔支付请求的 **伪代码**（20 行左右），要包含：幂等键检查、状态机条件更新、调用渠道（带熔断和有限重试）、超时后进入「待确认」状态并安排查单、成功后在同一个本地事务里写分录和发件箱。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- 幂等键的记录要保存多久？过期之后同一个键再来会怎样？
- 用户支付成功了，但订单服务因为消息丢了一直显示「待支付」，用户又付了一次。你的系统怎么发现、怎么处理？
- 退款也调用渠道，也可能超时。部分退款时，退款总额不能超过支付金额的约束怎么在并发下保证？
- 跨币种支付（买家付美元，卖家收人民币），汇率在什么时刻锁定？账本里怎么记？
- 怎么在不停机的情况下，把支付单表从一个数据库迁移到分库分表的集群上，并且迁移过程中一分钱都不能错？

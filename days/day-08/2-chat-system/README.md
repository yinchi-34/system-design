# Day 08 · 设计题：聊天系统（类 WhatsApp / 微信）

## 背景

聊天系统是系统设计面试里出现频率最高的题之一，因为它和前面学的「请求-响应」型系统（短链接、限流、爬虫）完全不同：

- **服务器要主动把消息推给客户端**。HTTP 是客户端问、服务器答，那「对方给你发了条消息」怎么让你的手机马上知道？（轮询、长轮询、WebSocket）
- **几亿条长连接** 挂在服务器上，连接是有状态的：用户 A 连在网关 3 上，用户 B 连在网关 17 上，A 发给 B 的消息怎么找到网关 17？
- **顺序**：同一个对话里，所有人看到的消息顺序必须一样。两个人同时发消息，谁在前？
- **离线**：B 不在线时消息存哪里？B 上线后怎么只拉取他没收到的那部分？B 有手机和电脑两台设备呢？
- **可靠**：网络随时会断，消息「至少一次」送达 + 客户端去重（Day 7）；已发送 / 已送达 / 已读三种回执。

今天的动手题（主从复制）在这里也会出现：消息存储怎么复制、用户刚发的消息刷新后能不能马上看到（读自己的写）。

## 题目

设计一个 **移动端即时通讯应用**。

**功能需求**

- 一对一聊天、群聊（群最多 **500 人**）。
- 文本消息为主；图片、语音、视频以附件形式发送（附件本身走对象存储，本题只需说明怎么接入）。
- 消息状态回执：已发送（服务器收到）、已送达（对方设备收到）、已读。
- 在线状态（「在线」/「最后上线时间」）。
- 离线消息：用户上线后能收到离线期间的全部消息。
- **多设备**：同一个账号可以同时登录手机、平板、电脑，所有设备都能收到消息，在一台设备上已读，其他设备也显示已读。
- 聊天记录在服务器上永久保存，换手机后可以拉取历史消息。

**非功能需求**

- 低延迟：双方都在线时，消息端到端延迟 p99 < 500 ms。
- 可靠：发送成功的消息不能丢；消息不能重复显示。
- 顺序：同一个会话里，所有参与者看到的消息顺序一致。
- 高可用：任何一台网关或存储机器宕机，用户最多感受到一次重连。

**规模（已知条件）**

- 日活 **5 亿**，同时在线峰值 **1 亿** 个连接（按设备算）。
- 每个日活用户平均每天发 **40** 条消息，平均每条 **100 字节**（不含附件）。
- 群消息占 20%，群平均 50 人。
- 一台网关服务器能维持 **50 万** 条长连接。
- 消息永久保存。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：每秒发送多少条消息（平均 / 峰值）？考虑群聊扇出后，每秒要 **投递** 多少条？每年新增多少存储（含 3 副本）？需要多少台网关？
2. **连接协议**（第 3 节）：短轮询、长轮询、WebSocket 各自的优缺点，你选哪个？心跳间隔怎么定？客户端断线重连时要做什么（补拉消息）？
3. **API / 消息协议**（第 3 节）：发消息、确认（ack）、拉取历史、已读回执分别是什么消息？客户端怎么给每条消息生成 **幂等 ID**，让网络重试不会产生重复消息？
4. **高层架构**（第 5 节）：画出 A 发一条消息给 B 的完整路径：客户端 → 网关 → 聊天服务 → 存储 → 找到 B 所在的网关 → 推给 B → B 回 ack。至少包括：长连接网关、会话路由（用户 → 网关的映射存在哪里）、聊天服务、消息存储、离线推送（B 不在线时走 APNs/FCM，Day 7）、在线状态服务。
5. **消息顺序与同步**（第 6 节，最重要）：
   - 每个会话的消息怎么编号？用 Day 6 的 Snowflake 全局 ID，还是 **每个会话一个递增序号**？各有什么问题？
   - 客户端怎么知道自己漏了消息、该从哪里补拉？（每个设备记住每个会话的「已同步到的序号」；或者每个用户一个「收件箱序号」）
   - 多设备同步：一台设备上发的消息、已读状态，怎么同步到同账号的其他设备？
6. **群聊**（第 6 节）：一条群消息是 **写扩散**（给每个成员的收件箱各写一份）还是 **读扩散**（只写一份到群的消息流，成员来读）？500 人的群各用哪种？为什么大群（比如几十万人的频道）的答案不一样？群消息的已读回执怎么做才不会爆炸（500 人每人回一次已读）？
7. **存储**（第 4、7 节）：消息表用什么存储、按什么分片（按会话 ID？按用户 ID？）？主键怎么设计才能高效地「拉取某个会话里序号大于 X 的消息」？为什么很多公司用 HBase / Cassandra 这类宽表存消息？消息存储的主从复制延迟会导致什么现象（发完刷新看不到），怎么用今天动手题的「读自己的写」解决？
8. **在线状态**（第 7 节）：1 亿在线用户，每个人上下线都要通知所有好友，会产生多大流量？怎么降低（按需订阅、合并、只对打开聊天窗口的好友推送）？
9. **取舍**（第 8 节）：至少 3 行，比如写扩散 vs 读扩散、全局 ID vs 会话内序号、推 vs 拉。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 6 节画出 **一条消息的时序图**：A 发送 → 服务器回「已发送」→ 推给 B → B 回 ack →「已送达」回给 A → B 打开 →「已读」回给 A。标出每一步如果网络断了会怎样、谁负责重试、怎么去重。
- 写清楚网关宕机时，挂在它上面的 50 万个连接会发生什么，以及客户端重连后怎么保证不丢、不重消息。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- 要做 **端到端加密**（服务器看不到消息内容），架构要怎么变？多设备下密钥怎么管理？服务器还能做哪些事、不能做哪些事（比如搜索聊天记录）？
- 用户删除一条已发送的消息（「撤回」），怎么让对方所有设备上都消失？对方离线呢？
- 网关要升级重启，怎么做到不让 1 亿用户同时掉线又同时重连（重连风暴）？
- 一个会话的消息序号由谁来分配？如果分配序号的服务是单点，挂了怎么办？如果是多主，怎么保证序号不冲突又有序？
- 消息存储保存了 10 年、几 PB 数据，绝大多数没人再看。怎么降低成本（冷热分层）？

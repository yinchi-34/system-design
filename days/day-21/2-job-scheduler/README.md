# Day 21 · 设计题：分布式任务调度器（类 Airflow / XXL-JOB / AWS EventBridge Scheduler）

## 背景

一个公司里有成千上万个「到点要做的事」：

- 每天凌晨 2 点：对账、生成报表、清理过期数据；
- 每 5 分钟：同步一次第三方的价格；
- 一次性的延迟任务：订单 15 分钟未支付自动取消、7 天后自动确认收货、优惠券到期前 1 天提醒——这类任务数量巨大，每天上亿个；
- 有依赖关系的任务流：「抽数据 → 清洗 → 训练模型 → 发布」，前一步成功了才能跑下一步。

如果每个服务都在自己的机器上用 `crontab` 或者 `sleep`，就会出现：机器挂了任务就不跑了；部署了 3 台机器，同一个任务跑了 3 遍；任务失败了没人知道；想看「昨晚的任务到底跑了没有」无处可查。

所以需要一个统一的 **分布式任务调度平台**。

## 题目

设计一个 **分布式任务调度器**。

**功能需求**

- 提交 **一次性延迟任务**：「在时间 T 回调这个 HTTP 接口 / 往这个消息队列发这条消息」。
- 定义 **周期任务**：cron 表达式（`0 2 * * *`），支持暂停、恢复、手动触发一次。
- **任务依赖**（DAG）：任务 B 和 C 依赖 A，D 依赖 B 和 C。
- 失败 **重试**（可配置次数和退避），超时控制，重试用完后告警。
- 查看每个任务每一次执行的状态、开始结束时间、日志。
- 支持任务 **优先级** 和按业务方的 **配额**（一个业务方不能占满所有执行资源）。

**非功能需求**

- **准时**：到点后 **1 秒内** 开始执行（周期任务和延迟任务）。
- **不丢**：已经提交成功的任务，一定会被执行（至少一次）。
- **尽量不重复**：同一次触发，正常情况下只执行一次；异常情况下允许重复，但要让业务能识别出来。
- 调度服务本身高可用，任何一台机器挂了都不影响。

**规模（已知条件）**

- 周期任务定义 **10 万** 个，平均每个每小时触发 **2** 次。
- 一次性延迟任务每天新增 **2 亿** 个，延迟时间从 1 秒到 30 天不等，大部分在 1 小时以内。
- 整点（尤其是凌晨 0 点、2 点）有大量周期任务同时触发，峰值可以到平均值的 **50 倍**。
- 每次执行记录保留 **30 天**。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：
   - 每秒要触发多少个任务（平均 / 整点峰值）？
   - 任意时刻有多少个「还没到点」的延迟任务在等着？存储要多大？
   - 30 天的执行记录有多少条、多大？
2. **API**（第 3 节）：创建延迟任务（带幂等键）、取消任务、创建 / 修改 / 暂停周期任务、手动触发、查询执行记录。执行方式怎么表达（回调 URL / 消息队列 topic / 注册的 worker 类型）？
3. **数据模型**（第 4 节）：
   - 任务定义表（周期任务：cron、下次触发时间、状态）、延迟任务表（`run_at`、状态、重试次数）、执行记录表。
   - 「按时间取出到点的任务」需要什么索引？MySQL 里 `WHERE run_at <= now() AND status = 'pending' ORDER BY run_at LIMIT 100` 在 2 亿行的表上能扛住吗？
   - 状态机：`pending → running → succeeded / failed → (retrying) → dead`。
4. **高层架构**（第 5 节）：API 服务、任务存储、**调度器**（决定什么时候、把哪个任务交出去）、**执行器 / worker**（真正执行）、执行记录、告警。调度和执行为什么要分开？画出一个延迟任务从提交到执行完成的路径。
5. **调度核心**（第 6 节，最重要）：
   - **到点检测**：每秒扫一次数据库？内存里维护一个堆（今天的动手题）？时间轮？Redis 有序集合？分别有什么问题？30 天后的任务也要一直放在内存里吗？（**分层**：远期的放数据库，快到点的预加载到内存）
   - **多台调度器怎么分工**：同一个任务不能被两台调度器同时触发。方案一：选一个 leader 负责调度（Day 15 Raft / Day 12 租约锁），其他待命；方案二：任务按 ID 分片，每台调度器负责一部分分片。各自的瓶颈和故障切换过程是什么？
   - **执行的可靠性**：任务交给 worker 以后 worker 挂了怎么办？（租约 + 心跳 + 令牌，今天的动手题）为什么这样做只能保证「至少一次」？业务方要怎么做幂等？
   - **周期任务**：调度器下线了 10 分钟，这期间应该触发 5 次的任务，恢复后补跑 5 次、补跑 1 次、还是不补？让用户怎么配置？上一次还没跑完，下一次又到点了怎么办？
6. **整点洪峰与隔离**（第 6 节）：
   - 凌晨 2 点几万个任务同时触发，怎么不把下游打垮？（错峰：允许在一个窗口内随机延迟；按业务方限流）
   - 一个业务方提交了 1000 万个任务，怎么不影响其他业务方？（配额、按租户分队列、公平调度）
   - DAG 任务：怎么判断一个任务的所有上游都完成了？一个上游失败了，下游怎么办？
7. **可靠性与扩展**（第 7 节）：
   - 调度器 leader 切换的那几秒，会不会漏掉任务或者重复触发？
   - 时钟：多台机器的时钟不完全一致，对「准时」和「不重复」有什么影响？
   - 执行记录量很大，怎么存、怎么清理？（按天分区、过期直接删分区）
   - 怎么监控调度器自己的健康？（「到点到开始执行」的延迟分布、积压任务数，Day 19）
8. **取舍**（第 8 节）：至少 3 行，比如单 leader vs 分片调度、内存堆 vs 时间轮 vs 数据库轮询、推（调度器调用 worker）vs 拉（worker 来取任务）、错过的周期任务补跑 vs 跳过。

## 面试追问（做完后自己先想想）

- 「订单 15 分钟未支付自动取消」：用延迟任务，还是用定时任务每分钟扫一遍「超过 15 分钟未支付的订单」？各自的优缺点？
- Kafka 不支持延迟消息，RocketMQ 支持固定的几个延迟级别（1s、5s、10s、30s、1m……）。为什么消息队列很难支持任意时间的延迟？
- 用 Redis 的有序集合做延迟队列，`ZRANGEBYSCORE` 取出到点的任务、再 `ZREM` 删除，多个消费者同时做会出什么问题？怎么改？（Lua 脚本原子操作）
- 30 天后才执行的任务，30 天里系统升级了、任务的回调接口改了，怎么办？

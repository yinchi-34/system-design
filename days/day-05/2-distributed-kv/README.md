# Day 05 · 设计题：分布式 KV 存储

## 背景

今天的动手题做了一台机器上的 KV：WAL 保证不丢，快照保证重启快。但一台机器有三个天花板：

- **容量**：一台机器几 TB 硬盘，数据有 100 TB 怎么办？→ 分区（Day 2 的一致性哈希）
- **可用性**：这台机器宕机、整个机房断电，服务就停了。→ 复制
- **吞吐**：一台机器每秒几万次读写，业务要一百万次怎么办？→ 分区 + 复制都能帮忙

一旦有了复制，就引出了分布式系统里最核心的问题：**多个副本怎么保持一致？网络断了怎么办？** Amazon Dynamo（以及受它启发的 Cassandra、Riak）、etcd / TiKV（Raft）、Redis Cluster，对这个问题给出了截然不同的答案。这道题是整个路线里后面很多天的「总纲」：Day 8 主从复制、Day 9 Quorum、Day 15 Raft、Day 16 Merkle 树、Day 22 Gossip 都会回到这里。

## 题目

设计一个 **分布式 KV 存储**，给公司内部的购物车、会话、用户偏好等服务使用。

**功能需求**

- `put(key, value)`、`get(key)`、`delete(key)`。key 最长 256 字节，value 最长 1 MB。
- 可以按需选择一致性：有的业务要求「写完马上能读到」，有的只要求最终一致、但写入永远不能失败（购物车「加入购物车」不能报错）。
- 支持 TTL（会话类数据过期自动删除）。

**非功能需求**

- 高可用：任意 1 台机器宕机不影响读写；**整个可用区（AZ）断掉**也不影响读写。
- 低延迟：读写 p99 < 10 ms（同地域）。
- 持久：写成功的数据不能因为单机故障丢失。
- 可扩展：加机器就能扩容量和吞吐，扩容过程中服务不停、迁移的数据量尽量少。

**规模（已知条件）**

- 总数据量 **100 TB**（不含副本），平均 value **1 KB**，key 平均 50 字节。
- 读 **100 万 QPS**，写 **20 万 QPS**（峰值是平均的 2 倍）。
- 每台存储机器：4 TB 可用 SSD，单机能扛 2 万 QPS 读写，10 Gbps 网卡。
- 一个地域 3 个可用区。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：一共有多少个 key？3 副本后总存储多少？需要多少台机器（分别按容量和按 QPS 算，取大的）？一台机器宕机，重新复制它的数据要多久？
2. **API 与数据模型**（第 3、4 节）：客户端 API 长什么样？一致性级别怎么让调用方选（比如 `consistency=ONE|QUORUM|ALL`）？每条数据除了 value 还要存什么元数据（版本号、时间戳、TTL、墓碑标记）？
3. **分区**（第 5、6 节）：怎么把 key 分到机器上？为什么用一致性哈希 + 虚拟节点（Day 2）？元数据（哪个 key 段在哪台机器）放在哪：中心化的元数据服务，还是每个节点都知道（Gossip）？客户端怎么找到对的节点？
4. **复制与一致性**（第 6 节，最重要）：二选一深入展开，并说明为什么另一种不适合这个场景：
   - **无主复制（Dynamo 风格）**：N 个副本、写 W 个、读 R 个。`W + R > N` 意味着什么？N=3 时 W/R 分别取多少，适合什么业务？两个客户端同时写同一个 key 产生冲突，怎么发现（向量时钟 / 版本向量）？怎么解决（最后写入者胜 LWW、交给客户端合并、CRDT）？LWW 依赖机器时钟，会出什么问题？
   - **有主复制（Raft / 主从）**：每个分区一个 Raft 组，写都走 leader。leader 挂了会怎样？选举期间这个分区多久不能写？读能不能走 follower？
5. **故障处理**（第 7 节）：
   - 临时故障：某个副本暂时连不上，写到哪里去（sloppy quorum + hinted handoff）？它回来以后怎么补数据？
   - 永久故障：副本之间长期不一致怎么发现和修复（读修复、后台用 Merkle 树做反熵，Day 16）？
   - 怎么判断一个节点「挂了」（心跳、Gossip、Day 22）？误判会怎样？
6. **单机存储引擎**（第 6 或 7 节）：每个节点内部怎么存？今天动手题的 WAL 在哪一层？为什么分布式 KV 大多用 **LSM 树**（RocksDB）而不是 B+ 树？删除为什么要写「墓碑」而不是直接删？墓碑什么时候能真正清掉？
7. **跨 AZ 放置**（第 7 节）：3 个副本怎么放才能扛住一整个 AZ 断掉？这会给写延迟带来多少代价？
8. **取舍**（第 8 节）：至少 3 行，比如 CP vs AP（CAP / PACELC）、无主 vs 有主、LWW vs 向量时钟、一致性哈希 vs 预分片（固定 16384 个槽，Redis Cluster 的做法）。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 6 节画出 **一次写请求** 的完整路径（客户端 → 协调节点 → N 个副本 → 每个副本的 WAL + memtable → 返回），标出在哪一步就可以给客户端返回成功，以及 W 个副本确认之前有副本宕机会怎样。
- 用一个具体例子说明冲突：两个客户端在网络分区的两侧同时修改同一个购物车，画出两个版本的向量时钟，以及合并之后的结果。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- N=3、W=2、R=2，写入成功后立刻读，一定能读到最新值吗？有没有反例？（提示：sloppy quorum、写失败但部分副本写进去了）
- 有一个超级热点 key（双十一首页配置），每秒 50 万次读，全打在同一组 3 个副本上。怎么办？
- 要支持跨 key 的事务（同时修改 A、B 两个 key），架构要怎么改？代价是什么？（两阶段提交、Percolator、Spanner）
- 跨地域（中国和美国）多活，两边都能写，写延迟要求 10 ms。还能做到强一致吗？为什么？
- 一台机器的硬盘慢了（不是坏了，只是 p99 从 2 ms 变成 200 ms），整个集群的 p99 会怎样？怎么发现和规避？

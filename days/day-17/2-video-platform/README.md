# Day 17 · 设计题：视频平台（类 YouTube / B 站 / 抖音）

## 背景

视频平台看起来就是「上传一个文件，别人点开播放」，但它和前面的题有几个本质区别：

- **写入很重**：一个 1 GB 的原始视频上传以后，要先转码成多种分辨率（240p / 480p / 720p / 1080p / 4K）和多种编码格式，才能给不同网速、不同设备的人看。转码非常耗 CPU，一个视频可能要几分钟到几小时。
- **读取更重**：热门视频一天被看几千万次，带宽成本是整个平台最大的一项开销。→ **CDN** 几乎扛下所有流量。
- **播放要流畅**：用户的网速时快时慢。→ **自适应码率**（HLS / DASH）：视频切成几秒一段，播放器根据网速动态选择每一段的清晰度。
- **上传要可靠**：大文件、弱网。→ 今天动手题的分块上传和断点续传。

## 题目

设计一个 **视频平台**。

**功能需求**

- 用户上传视频（最大 **10 GB**），可以填写标题、描述、封面。
- 上传完成后，视频经过 **转码**、生成缩略图、内容审核，然后才对外可见。上传者能看到处理进度。
- 用户观看视频：根据网速 **自动切换清晰度**，也可以手动选择；支持拖动进度条。
- 视频的观看次数、点赞、评论（点赞和计数见 Day 13，这里不展开）。
- 首页推荐、搜索：不展开，只说明需要哪些数据。

**非功能需求**

- 播放：首帧时间 **< 2 秒**，播放过程中尽量不卡顿。全球用户都要能流畅观看。
- 上传：弱网可续传，已上传的视频 **绝对不能丢**。
- 处理：普通视频上传完成后 **几分钟内** 可以观看。
- 高可用：观看服务 99.99%，上传和转码可以稍低。

**规模（已知条件）**

- 日活 **10 亿**，每个日活用户每天平均观看 **5** 个视频，每个视频平均观看 **5 分钟**。
- 平均播放码率 **2 Mbps**（混合各种清晰度后）。
- 每天上传 **50 万** 个视频，平均原始大小 **300 MB**、平均时长 **10 分钟**。
- 转码后所有清晰度加起来，大约是原始文件大小的 **1.5 倍**。
- 存储 3 副本（或等价的纠删码）。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：
   - 每天的播放流量是多少（字节 / 天），平均和峰值出口带宽是多少 Gbps？为什么这个数字决定了 CDN 是必需品？
   - 每天新增存储（原始 + 转码后，含副本）？一年呢？
   - 平均每秒上传多少个视频？如果转码一个 10 分钟的视频需要 **20 分钟** CPU 时间（所有清晰度合计），需要多少个 CPU 核一直在转码？
2. **API**（第 3 节）：上传（创建会话、上传分块、完成，可以直接引用动手题）、查询处理状态、获取视频元数据和播放地址、观看。播放地址返回什么（一个 HLS / DASH 的清单文件 URL）？
3. **数据模型**（第 4 节）：
   - 视频元数据表（视频 ID、上传者、标题、状态、时长、各清晰度的清单地址……），用什么数据库？
   - 视频状态机：`uploading → uploaded → processing → ready / failed / rejected`。谁来推进状态？
   - 视频文件本身存在哪里（对象存储），路径怎么组织？原始文件转码完以后还要留着吗？
4. **高层架构**（第 5 节）：画出两条路径：
   - **上传路径**：客户端 → 上传服务（分块 / 续传）→ 对象存储 → 消息队列 → 转码流水线 → 写回元数据 → 通知上传者。
   - **观看路径**：客户端 → API 拿元数据和清单地址 → CDN → 回源到对象存储。
5. **转码流水线**（第 6 节，最重要）：
   - 为什么上传完成和转码要通过 **消息队列** 解耦，而不是上传服务直接调用转码？（Day 7）
   - 一个 2 小时的视频，单机转码太慢。怎么 **切分** 成很多小段并行转码，最后再拼起来？画出这个 DAG（切分 → 每段转多个清晰度 → 合并 → 生成清单 / 缩略图 / 审核）。
   - 转码任务失败了、Worker 挂了怎么办？任务要 **幂等**，为什么？
   - 怎么让上传者尽快看到结果？（比如先出 360p 就对外可见，高清晰度后台继续转）
6. **播放与 CDN**（第 6 节）：
   - 解释自适应码率：视频切成多少秒一段？清单文件里有什么？播放器怎么决定下一段用哪个清晰度？
   - 拖动进度条为什么也变简单了？
   - 热门视频和长尾视频（绝大多数视频只有很少的人看）在 CDN 上的命中率有什么不同？长尾视频怎么办？
   - 新视频刚发布，几百万人同时点开（比如大主播），CDN 上还没有缓存，怎么防止同时回源压垮对象存储？（请求合并 / 预热，Day 4）
7. **可靠性与扩展**（第 7 节）：
   - 观看次数每秒几十万次写，怎么计？（Day 13）
   - 内容审核放在流水线的哪一步？审核没通过但已经被 CDN 缓存了，怎么办？
   - 版权保护 / 防盗链：怎么让 CDN 上的视频地址不能被随便拿去别的网站播放？（签名 URL + 过期时间）
   - 原始文件和冷门视频的存储成本怎么降？（冷热分层、低频存储）
8. **取舍**（第 8 节）：至少 3 行，比如分段长度（短 vs 长）、转码的清晰度档位多 vs 少、提前转好所有清晰度 vs 按需转码、自建 CDN vs 买 CDN。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 5 节两条路径都要画出来，并标出哪些步骤是同步的、哪些是异步的。
- 第 6 节画出转码 DAG，并说明一个视频的状态在什么时刻从 `processing` 变成 `ready`。
- 第 2 节要算出出口带宽，并据此说明架构里最贵的部分是什么。
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- 用户上传成功以后，应该在哪一步告诉他「上传成功」？上传完成、转码完成、还是审核通过？各自对用户体验和系统设计有什么影响？
- 同一个视频被不同的人重复上传了 1000 次（搬运），怎么发现？完全相同的文件好办（秒传），剪掉开头 3 秒、加了水印的怎么办？（视频指纹）
- 直播和点播的架构有什么不同？延迟要求从「几分钟内可看」变成「几秒内」，哪些环节要改？
- 一个国家的 CDN 节点全部故障，怎么让那里的用户继续看？
- 推荐系统需要知道「用户看了哪些视频、看了多久」，这些数据怎么从播放器收集回来？（埋点 → 消息队列 → 流处理 / 离线计算）

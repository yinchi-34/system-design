# Day 18 · 设计题：热搜 / 趋势话题（类微博热搜 / Twitter Trends）

## 背景

热搜榜是全站流量最大的入口之一：上了热搜的话题，几分钟内就会被几千万人点开。它要做的事情可以一句话说清楚：**持续地从海量的搜索和发帖里，找出「最近突然变热」的话题，几十秒更新一次。**

难点在于：

- **输入量巨大**：每秒几十万次搜索、几万条新帖子，每条帖子里还要抽取话题词。
- **要的是「趋势」而不是「总量」**：「天气」「快递」每天都被搜很多次，不应该一直在榜上。热搜要找的是 **比平时多得多** 的词。
- **要快**：一个新闻爆出来，几分钟内就应该上榜。用每天跑一次的离线计算是不行的 → **流式计算**。
- **要准也要稳**：榜单不能被刷（水军、机器人），也不能每 10 秒就剧烈抖动一次。

## 题目

设计一个 **热搜 / 趋势话题服务**。

**功能需求**

- 全站热搜榜：前 **50** 名，每 **30 秒** 更新一次。
- 分地区的热搜榜（全国 + 34 个省份），以及分类榜（娱乐、体育、科技……）。
- 每个上榜话题显示一个热度值和标签（「新」「热」「爆」）。
- 运营可以人工干预：屏蔽某个词、置顶某个话题。
- 用户点开榜单的延迟 **< 100 ms**。

**非功能需求**

- 从一个话题开始暴涨到出现在榜上，**< 2 分钟**。
- 榜单读取的可用性 99.99%（宁可显示 30 秒前的旧榜，也不能打不开）。
- 计算链路可以偶尔丢一点数据（近似就够），但不能长时间停摆。
- 抗刷：少数账号的集中刷量不应该让一个词上榜。

**规模（已知条件）**

- 日活 **3 亿**，每个日活用户每天平均搜索 **10** 次、看榜单 **5** 次。
- 每天新发帖子 **2 亿** 条，平均每条抽取出 **2** 个话题词。
- 每天出现过的不同话题词约 **5000 万** 个，其中 **90%** 一天只出现不到 10 次。
- 峰值是平均值的 **5 倍**（重大新闻时可能是 20 倍）。

## 要回答的问题

全部写在 `DESIGN.md` 里，下面这些问题一定要覆盖到：

1. **估算**（第 2 节）：
   - 每秒有多少个「话题事件」（搜索 + 帖子里的话题词），平均和峰值？
   - 精确统计「每个词最近 5 分钟的次数」需要多少内存？用 CMS（宽 `2^16`、深 `5`、每格 4 字节）呢？
   - 榜单读取的 QPS 是多少？为什么这部分反而是最简单的？
2. **API**（第 3 节）：获取热搜榜（地区、分类）、上报事件（内部接口，或者直接走消息队列）、运营后台的屏蔽 / 置顶。榜单接口返回什么字段？
3. **数据模型**（第 4 节）：
   - 原始事件放在哪里（消息队列，保留多久）？
   - 计算出来的榜单存在哪里、什么格式（Redis 里一个序列化好的列表，带版本号）？
   - 每个词的 **历史基线**（过去 7 天同一时段的平均次数）存在哪里？
   - 屏蔽词、置顶这些运营配置存在哪里，怎么下发到计算节点？（Day 15 配置中心）
4. **高层架构**（第 5 节）：画出 搜索服务 / 发帖服务 → 消息队列 → 流式计算（预聚合 → 全局汇总 → 打分排序）→ 榜单存储 → 榜单 API（多级缓存）→ 客户端。标出哪些地方是近似的、哪些是精确的。
5. **流式计算**（第 6 节，最重要）：
   - 为什么不能让所有事件都发到一台机器上计数？怎么做 **两级聚合**：先在很多台机器上按词局部计数（或者各自维护一个 CMS + Top-K），再汇总到一台机器上合并？只合并每台机器的 Top-K 候选会漏掉什么？（提示：一个词在每台机器上都只是第 51 名）
   - 滑动窗口怎么实现（今天的动手题：分桶 + 合并）？窗口多长、桶多大，各有什么影响？
   - **热度打分**：用「当前窗口的次数」和「历史基线」怎么算出一个「突增程度」？基线是 0 的新词怎么办？给出你的公式并说明理由。
   - 怎么防止榜单剧烈抖动？（平滑、名次变化设门槛、上榜后最短停留时间）
6. **抗刷与治理**（第 6 节）：
   - 同一个用户搜 1000 次同一个词，应该算几次？怎么在流里按「用户 + 词」去重（布隆过滤器 / HyperLogLog 算独立用户数，Day 4、Day 13）？
   - 用「独立用户数」而不是「次数」打分，有什么代价？
   - 敏感词屏蔽放在计算前还是计算后？
7. **可靠性与扩展**（第 7 节）：
   - 汇总节点挂了怎么办？重启后窗口里的数据怎么恢复（从消息队列重放 / 定期快照）？
   - 榜单 API 每秒几万次读，怎么扛？（本地缓存 + Redis + CDN，30 秒才变一次）
   - 分地区、分类榜单：是每个榜单一套计算，还是在一套计算里多维度计数？
8. **取舍**（第 8 节）：至少 3 行，比如精确计数 vs CMS、窗口长 vs 短、按次数 vs 按独立用户数、实时性 vs 榜单稳定性。

## 要求

- 限时 45 分钟，前 5 分钟只做需求澄清和估算。
- 第 5 节画出完整的数据流，并标出每一级的并行度和每一级的数据量（每秒多少条）。
- 第 6 节写出你的热度打分公式，并用一个例子算一遍：「天气」平时每 5 分钟 1 万次、现在 1.2 万次；「某明星官宣」平时 0 次、现在 8000 次。谁该上榜？
- 每个技术选型都要写「为什么」和「放弃了什么」。写不出来的地方先空着，标 `TODO`。

## 面试追问（做完后自己先想想）

- 如果要求「严格精确」的前 50 名，架构要怎么改？代价是多少？产品上真的需要吗？
- 一个热点事件被不同的人用十几种不同的说法搜索（「XX 官宣」「XX 结婚」「XX 恋情」），它们的热度被拆散了，可能一个都上不了榜。怎么办？（话题聚类）
- 事件时间和处理时间不一致（手机离线了 10 分钟才上报），这些迟到的事件应该算进哪个窗口？（流计算的水位线 / watermark）
- 热搜本身会带来更多搜索（上榜 → 更多人点 → 更热），这个正反馈怎么处理？

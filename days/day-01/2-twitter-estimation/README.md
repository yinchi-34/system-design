# Day 01 · 设计题：Twitter 规模的容量估算

## 背景

几乎每道系统设计题都要在开头花 5 分钟做 **封底估算**（back-of-the-envelope estimation）。面试官不在乎数字精确，在乎的是：你的假设是否合理、推导是否清楚、算出来的数字能不能指导后面的设计决策（要不要分片、缓存多大、要几台机器）。

今天只练这一件事，把它练成肌肉记忆。

## 题目

估算一个 Twitter 规模的社交平台需要多少资源。你需要 **自己给出假设**，并写清楚每一步怎么算出来的。

已知（可以直接用，也可以说明理由后修改）：

- 月活 MAU：5 亿，日活 DAU 约为 MAU 的 40%
- 每个日活用户平均每天发 2 条推文
- 每个日活用户平均每天刷新时间线 10 次，每次加载 20 条推文
- 约 15% 的推文带图片，约 2% 带视频
- 数据保存 5 年

## 要回答的问题

在 `DESIGN.md` 的「2. 规模估算」里回答下面每一项，写出公式和结果：

1. 写 QPS：平均值和峰值（峰值倍数自己假设并说明）。
2. 读 QPS（时间线读取 和 推文读取）：平均值和峰值。读写比是多少？
3. 存储：
   - 单条推文的文本 + 元数据大概多大？列出字段估算。
   - 5 年纯文本存储总量。
   - 5 年图片和视频存储总量（单张图片 / 单个视频的大小自己假设）。
4. 带宽：入口（写）和出口（读）各多少，媒体是否计入要说清楚。
5. 缓存：如果要把「最近 1 天的推文」或「活跃用户的时间线」放进内存，需要多少内存？大概要几台 64 GB 内存的缓存机器？
6. 机器数：假设一台应用服务器能扛 1 万 QPS，读服务需要多少台？
7. 结论：根据上面的数字，**列出 3 个对后续架构有直接影响的结论**（例如「写 QPS 不高，单主库够用」或「媒体存储占绝对大头，必须用对象存储 + CDN」）。这一项最重要。

DESIGN.md 里其他章节今天可以只写几行：需求澄清写下你的假设范围，高层架构画一张最粗的图即可。

## 常用数字（背下来）

| 量 | 近似值 |
|----|--------|
| 1 天 | 86,400 秒 ≈ 10^5 秒 |
| 100 万次/天 | ≈ 12 QPS |
| 1 亿次/天 | ≈ 1,200 QPS |
| 2^10 / 2^20 / 2^30 / 2^40 | ≈ 千 / 百万 / 十亿 / 万亿 |
| 内存随机读 | ~100 ns |
| SSD 随机读 | ~100 µs |
| 同机房往返 | ~0.5 ms |
| 跨洲往返 | ~150 ms |

## 要求

- 限时 30 到 45 分钟，像在白板上一样写，不要查资料。
- 数字取整，用科学计数法或 K/M/B/TB/PB，保留 1 到 2 位有效数字就够。
- 每个结果都要能看出是怎么算来的。

## 面试追问（做完后自己先想想）

- 如果明星用户（1 亿粉丝）发一条推，你的读写估算会怎么变？推模式和拉模式各自的代价是多少？
- 峰值倍数你取了多少？在热点事件（世界杯决赛）时可能到多少，系统怎么应对？
- 你的存储估算里有没有算副本？3 副本之后是多少？
